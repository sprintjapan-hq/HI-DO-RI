# HI-DO-RI 機能リリースパイプライン

このドキュメントは、HI-DO-RIにおける機能追加のプロセスと各ゲートを定義します。

## リリースプロセス

### 1. 要望受付
- `/feature-request` フォームから要望を受け付け
- Slack `#hi-do-ri_feedback` へ自動通知（追加のSlack送信は不要）
- 要望内容を運営チームで確認

### 2. 分析と仕様策定
- 要件分析を実施
- 機能仕様を作成
- 成功基準を明確化

### 3. 承認プロセス
- 夏本による機能内容・仕様の承認
- HD企画によるGo/No-Go判断
- **承認前の実装は禁止**

### 4. バージョンID予約
- 最新の公開バージョン（`vX.Y`）に0.1を加算
- バージョンIDは再利用しない
- **注意**: 管理画面の「完了通知」（`完了 #n` 形式）は使用しない

### 5. 実装
- GitHubリポジトリ `sprintjapan-hq/HI-DO-RI` で実装
- Replit Publishで公開
  - Replitログイン・Cloudflare設定は人手で対応
  - 夏本へのプロンプト転送やPublishクリック依頼は不要

### 6. レビューとテスト
- review.mdを作成
- preview-test.mdで検証
- 成功基準を満たすまで修正ループ

### 7. 最終仕様確定
- final-spec.mdにバージョンIDと共に仕様を記録

### 8. 機能履歴への追加
- `/feature-history` ページにバージョンカードを追加
- 既存のハードコードされたカード形式を使用

### 9. デプロイと本番テスト
- deploy.mdを作成
- プレビューと同じテストケースで本番環境を検証
- 歩験11（本番最終試験）を実施

### 10. フィードバック監視
- 本番テスト後、`#hi-do-ri_feedback` で条件まわりの再苦情の有無を確認
- 推測数値は記録しない
- 実際の報告内容のみを記録

### 11. リリース報告
- HI-DO-RI運用チャンネルで報告
- **実施しないこと**:
  - メール送信
  - 追加のSlack通知
  - シークレット値のローテーション
  - 架空の数値（ユーザー数、メトリクスなど）の報告
  - 完了通知の使用

## 重要な注意事項

- 各ステップのドキュメントは `docs/releases/vX.Y/` に保存
- 事実に基づいた記録を維持し、架空の情報を含めない
- Clerk、Googleカレンダー、プライバシーポリシーなど無関係な機能には触れない
